프로젝트 전체 지도

STOCK-ANALYZER-KR, 한국 주식 조건 스크리닝 정보 서비스를 구조·흐름·개념·장단점으로 풀어 쓴 안내서입니다.

기준: 2026-10-06 저장소 파일(HANDOFF.md, decisions.md DEC-001~092, 코드, QA 결과서)을 직접 읽고 작성. 파일에서 확인하지 못한 내용은 미확인 표시.

1. 한눈에 보기

이 서비스는 무엇인가. 공공 일봉 데이터로 등락률, 이동평균 이격도, 거래량 이상치, 패턴 지표 같은 값을 미리 계산해 두고, 사용자가 건 조건에 맞는 종목을 걸러 보여 주는 정보 도구입니다. "이 종목을 사세요"라는 투자 권유는 하지 않습니다(화면 문구는 lint:copy 검사가 막습니다). 사용자는 정보를 보고 투자 방향을 스스로 정합니다.

누가 쓰나 (1) 내 PC 로컬 모드

관리자 한 명(본인)이 자기 노트북에서 씁니다. Docker DB, API(4001), 웹(4000), 스케줄러가 전부 내 PC에서 돕니다. 증권사 앱키로 장중 시세, 실시간, 장중 재계산까지 쓸 수 있습니다.

누가 쓰나 (2) 운영 사이트

가입 후 관리자 승인을 받은 회원이 쓰는 사이트(Render + Neon). 일봉 기반 화면만 있고 증권사 시세 기능은 화면에도 요청에도 없습니다. 지금은 사용자 지시로 Render 배포를 하지 않습니다.

현재 상태 5가지

  1. 일봉 수집 → 가공 → 발행 파이프라인과 조건·패턴 스크리닝, 종목 상세, 시장 요약, 관심종목, 로그인·관리자 승인이 구현돼 있습니다.
  2. 로컬 모드에 증권사 시세 기능이 붙었습니다: 장중 분·틱 차트, 실시간(웹소켓), 전 종목 준실시간 시세, HTS 조건검색 화면, 장중 재계산(DEC-089~091).
  3. 2026-10-06 최상위 목표는 "실시간 데이터를 보고 투자 방향은 본인이 정한다"입니다(HANDOFF).
  4. DEC-092로 "공개 전 날짜를 영구히 건너뛰던" 따라잡기 결함을 고쳤습니다. 사용자 PC에서 fix_local_data.ps1을 다시 돌려 확인하는 일이 남아 있습니다.
  5. 실제 증권사 응답은 개발 환경에서 한 번도 확인하지 못했습니다(앱키 없는 모의 서버 시험). 사용자가 장중에 확인 도구를 돌려야 합니다.

3. 전체 흐름

A. 하루 데이터 흐름

B. 화면 요청 흐름

  1. 브라우저가 웹 서버(Next.js)에 페이지를 요청합니다. 로그인이 켜진 환경이면 세션을 확인하고, 없으면 로그인 화면으로 보냅니다.
  2. 웹 서버가 대신(BFF) API를 호출합니다. 운영에서는 내부 토큰이 없는 API 호출을 거부하도록 설정돼 있어(PUBLIC_API_REQUIRE_INTERNAL_TOKEN) 웹 서버만 API를 부를 수 있습니다.
  3. API(api_service 계정)가 public_serving의 현재 발행된 거래일 기준으로 읽기 전용 조회를 합니다. 입력값 검증, 요청 속도 제한이 걸립니다.
  4. JSON 봉투({data, meta, error})로 돌려주고, 화면은 "데이터 기준일"을 함께 보여 줍니다.

C. 장중 기준 흐름 (내 PC, 관리자 전용)

  1. 시세 폴러가 증권사 REST로 전 종목 시세를 돌아가며 받아 메모리에 쌓습니다(한 바퀴 수십 초 추정). 화면에 보이는 상위 최대 200종목은 우선 순환으로 약 3초 간격입니다.
  2. 발행 일봉이 직전 거래일보다 뒤처졌으면(최대 5거래일) 증권사 일봉으로 빠진 날만 보충합니다. 발행 일봉과 종가가 다른 종목은 교차검증에서 결과에서 뺍니다(DEC-090).
  3. 일봉 이력 + 오늘 행(현재가·누적 거래량)으로 지표를 배치와 같은 순수 함수로 재계산합니다.
  4. 재계산한 행을 JSON으로 DB에 넘겨 jsonb_to_recordset 가상 테이블로 기존 판정 SQL을 그대로 돌립니다(Python 재판정 없음).
  5. 결과를 스냅샷(snapshot_id)으로 고정합니다. 화면은 기본 10초마다 자동 갱신하고, 새로 들어온 종목은 "신규", 빠진 종목은 "최근 변화"에 보여 줍니다. "일시정지"하면 그 순간 결과에 고정됩니다.

근거: docs/stock-detail/10-intraday-rescreen-contract.md, docs/ops/local-live-screen-guide.md.

D. 로그인·권한 흐름

  1. 가입하면 대기 상태가 되고, 관리자가 승인해야 쓸 수 있습니다(DEC-074). 계정은 auth 스키마에만 있고 auth_service 계정만 접근합니다.
  2. 로그인 실패가 쌓이면 잠금 단계가 올라갑니다(회원 테이블 app_users의 failed_attempts, lockout_level, locked_until).
  3. 권한은 일반(user)과 관리자(admin). 투자자별 수급 탭과 회원 관리는 관리자 전용입니다.
  4. 로컬 전용 API는 거기에 로컬 모드 4중 통제가 더해집니다(다음 장 참고).

4. 핵심 개념 사전

발행 거래일
화면에 "지금 쓰이는" 데이터가 어느 날 것인지 가리키는 날짜. 가공이 끝나 검증된 거래일로 발행 포인터(current_published_batch)가 옮겨질 때만 바뀝니다. 포인터가 안 움직이면 화면은 예전 날짜에 머뭅니다.
+1영업일 지연
공공데이터포털 일봉은 장이 끝난 그날이 아니라 다음 영업일 이후에 올라옵니다. 그래서 일봉 기반 화면은 구조적으로 하루 늦습니다. 휴일이 끼면 더 늦습니다.
따라잡기 (catch-up)
빠진 날을 스스로 채우는 기능. 최근 10거래일 중 가공이 안 끝난 날을 오래된 순으로 채워, 며칠 실패하거나 PC가 꺼져 있어도 다음 실행이 복구합니다.
NOT_PUBLISHED
"아직 공공데이터가 안 올라왔다"는 뜻의 배치 결과. 오류가 아니라 기다림이며, 재시도 횟수에 세지 않습니다(DEC-092).
가공 지표
원본 시세 대신 보여 주는 계산값: 등락률, 이동평균 이격도(5·20일), 거래량 이상치 점수, 패턴 지표(조건 c1~c9, 압축 정도를 보는 10개 선발 기준 중 데이터가 있는 것).
백분위
PER·PBR·시가총액은 원값 대신 "전체 중 어느 위치인가"로 노출합니다(*_percentile). 원시값(*_raw)은 응답에서 제외됩니다.
basis (live / daily)
장중 기준 결과의 각 종목이 오늘 시세로 계산됐는지(live) 어제 일봉 값 그대로인지(daily) 표시. 숨기지 않고 "일봉" 표지로 보여 줍니다.
스냅샷
어느 시점의 계산 결과를 통째로 고정한 것. 페이지를 넘겨도 같은 결과를 보려고 씁니다(최근 5개 보관).
우선 순환
전 종목 시세는 느리게 돌되, 화면에 보이는 종목만 3초 안팎으로 더 자주 받는 방식.
일봉 보충과 교차검증
장중에는 발행 일봉이 어제도 못 따라온 날이 많아, 증권사 일봉으로 빠진 날만 임시로 채웁니다. 겹치는 날의 종가가 발행 일봉과 다르면(액면분할 등) 그 종목은 계산에서 뺍니다.
로컬 모드 4중 통제
코드(require_local_mode)에서 확인한 조건: ① LOCAL_INTRADAY_ENABLED 켜짐 ② 프록시 헤더 없음 ③ 접속 IP가 허용 목록(기본 127.0.0.1, ::1) ④ Host 헤더가 사설 주소. 하나라도 어긋나면 "존재하지 않는 기능"처럼 404로 응답합니다. 로그인을 켠 환경에서는 관리자만 통과합니다.
개인 로컬 vs 운영
증권사 시세는 개인 이용 전제의 앱키로 받아 내 PC에서 나만 봅니다. 운영 사이트로 재배포하면 약관 문제가 될 수 있어 서버 경유는 약관 확인 전까지 쓰지 않습니다(HANDOFF).

5. 장점

장점구체적 근거
원본 시세 비노출을 구조로 강제3중 방어: raw_internal 스키마 분리, api_service에 권한 없음, 배치와 API 프로세스 분리(03-system-design.md §1-1). 개발자 실수로는 새기 어렵습니다.
판정 SQL 단일 출처조건 판정은 screen_repository.py/pattern_repository.py 한 곳. 장중 재계산도 판정을 복제하지 않고 입력 행만 가상 테이블로 바꿉니다(계약서 §1). 가상 행=발행 행이면 결과가 기존과 같아야 한다는 동치 시험이 있습니다.
역할별 DB 권한 분리migrator, batch_worker, api_service 역할(deploy/db/init/01-roles.sh)과 auth 전용 auth_service(마이그레이션 0015).
멱등 배치와 따라잡기하루 두 번 돌려도 안전, 빠진 날 자동 복구, PostgreSQL 잠금으로 동시 실행 방지(shared/batch_lock.py), 서킷브레이커.
정직한 표시지연·부분값·일봉 고정을 숨기지 않고 표지로 보여 줍니다(거래량 부분값 경고, "일봉" 표지, 제외 종목 수).
운영 빌드 비노출로컬 전용 기능은 운영 빌드에서 화면도 요청도 없음이 시험으로 확인됐습니다(docs/qa/2026-10-06-psearch-integration-test-result.md 외).
시험 규모파이썬 시험 파일 74개(unit 53, integration 21), def test_ 함수 약 940개, 전체 회귀 1,469개 통과·0 실패(파라미터 확장 포함). 프런트 점검 스크립트 16개 + 금지 문구 검사 + 브라우저 시험(장중 기준 화면 160·17·26, 종단 29·6, 로그인 켠 로컬 61). PowerShell 실행 시험 22개. 에이전트가 직접 시험한다는 규칙을 CLAUDE.MD 상시 규칙으로 명문화.
결과서·결정 로그 문화docs/qa/에 결과서·화면 캡처 폴더 등 38개 항목, DEC 92건이 append-only로 쌓여 "왜 이렇게 했는가"가 남습니다. 새 담당자가 HANDOFF와 decisions만 읽고 이어받는 구조입니다.
되돌릴 길2개 서비스 구성 파일을 롤백용으로 보관(deploy/render/render.two-services.yaml), 알려진 한계를 문서에 적어 둠.

6. 단점·위험

위험내용과 근거위험도
일봉이 +1영업일 늦음공공데이터가 다음 영업일 이후 공개라 일봉 화면은 구조적으로 하루 늦습니다. 정확한 공개 시각도 미실측. 장중 재계산이 이를 보완하지만 내 PC 전용입니다.높음
단일 PC 스케줄러 의존주 실행이 내 노트북의 Windows 작업 스케줄러입니다. 꺼져 있으면 수집이 안 되고, 켜진 뒤 따라잡기로만 복구합니다. 보조로 만든 scheduled-batch.yml은 GitHub에 등록돼 있지 않습니다(GitHub는 기본 브랜치 main에 있는 워크플로만 인식하는데 main에는 이 파일이 없음 — Actions API로 확인: 등록된 워크플로는 render-deploy 하나뿐). 사용자 결정 대기높음
실제 증권사 응답 미확인개발 환경에서 증권사 서버로 나갈 수 없어 앱키 없는 모의 서버로만 시험했습니다. 응답 필드·수정주가 기준·조건검색 갱신 여부는 사용자 장중 확인 대기(kis_*_smoke_test.py).높음

  1. 정부가 공개하는 주식 일봉 데이터를 매일 내려받아 내 서버 DB에 쌓습니다.

  3. 사용자가 조건을 걸면 그 계산값으로 해당 종목만 골라 웹 화면에 보여 줍니다.
  4. 정부 데이터는 하루 늦기 때문에, 내 PC에서만 증권사 시세를 붙여 장중에 다시 계산합니다.
  5. 투자 추천은 하지 않고, 원본 시세는 밖으로 안 새도록 DB 구조로 막아 둡니다.
