## 1. 서비스/기능 개요 및 목적
**"시니어 생활팁" 유튜브 채널의 기존 영상 제목을 안전하게 개선하는 로컬 Python CLI 프로그램.** 채널 소유자(사용자)가 별도로 만든 제목 후보를 파일로 입력하면, 프로그램이 (1)시니어 시청자 특화 규칙으로 후보를 검증·차단하고, (2)사람 승인 후에만 `videos.update`로 제목만 바꾸며, (3)모든 변경을 기록하고 한 번에 롤백할 수 있게 하고, (4)변경 전후 성과 지표를 수집·비교한다.

**목적**: 계정 제재 위험을 최소화하면서 제목 개선 과정을 자동화하고 기록한다(v1 §3). 제목을 "더 자극적으로"가 아니라 **"더 정확하고 안전하게"** 만드는 것이 목적이다.

## W1. 서비스/기능 개요와 목적 (웹)
**ytitle 웹 = 기존 CLI(ytitle)를, 채널 소유자 1인이 자기 PC의 Docker에서 `http://127.0.0.1:8080`으로만 쓰는 웹 프로그램으로 바꾼 것.** 내 채널 영상 약 200개의 제목을 AI가 제안하고, 기존 검증기가 통과/경고/차단을 판정하며, 사람이 확인·승인한 것만 하루 상한 안에서 여러 날에 걸쳐 일괄 반영하고, 이력·롤백·성과 비교를 제공한다.

- **왜**(요청서 §2-1): CLI는 후보 1건씩 반영·하루 3건·72시간 간격이라 200개 일괄 처리에 맞지 않고, 후보를 사람이 파일로 써야 하며 AI 제안이 없다.
- **현재 구현 범위 = M1 데모 모드**(DEC-038): 가짜 영상 200개, 모의 AI(`web/backend/ytweb/ai/mock.py`), 모의 유튜브 게이트웨이(`youtube/mock.py`). **구글·AI 실호출 코드는 저장소에 없다**(`ytweb/config.py`의 `MODES = ("demo",)`, `ai/factory.py`는 demo일 때 `MockSuggester`만 반환, 라이브 게이트웨이 클래스 부재). 실서비스 연동은 M2(구글 읽기)·M3(실제 AI·라이브 반영, 사용자 승인 후).
- **as-built 구성**(compose 5서비스, `web/compose.yaml`): `web`(nginx-unprivileged, 호스트 `127.0.0.1:8080` 단독 게시) · `api`(FastAPI) · `worker`(같은 이미지) · `migrate`(1회, 소유자 계정) · `db`(PostgreSQL 17, internal 네트워크, 호스트 포트 없음). 코어 `src/ytitle`는 복사 없이 `PYTHONPATH`로 재사용(`web/docker/api.Dockerfile`).

## W6. 제약 조건
- **예산**: 추가 비용 0원 목표(개인 도구, 무료 API 쿼터). **M3의 AI 호출 비용은 미정**(Q-1 확정 전 상한 설정 불가). Docker Desktop 라이선스는 사용자 확인(Q-9, 법적 판단 아님).
- **일정**: 미정(Q-2-2). 사용자 지시는 "개발 1차 목적, 최대한 빨리"(DEC-038) → 마일스톤 M1(데모) 완료, M2~M4 대기.
- **인력**: 사용자 1인 + AI 에이전트 병렬 팀(백엔드 2, 프런트 1, 인프라 1).
- **쿼터 산식(가정, 원문 미열람)**: 기본 10,000단위/일, 앱 정책 `daily_limit_units: 6000`(`config/settings.yaml`), 반영 1건당 52단위 선예약(재조회 1+갱신 50+검증 재조회 1). 상한 10건/일이면 일 520단위, 20건/일이면 1,040단위 — 정책 한도 안. **200개를 영상당 1회 반영한다면 10건/일 20일, 20건/일 10일**(산술).
- **기술 제약(as-built)**: Windows + Docker Desktop(WSL2) 가정(A-W1, 미확인), 호스트 포트 8080 고정(사용 가능 여부 미확인), Python 3.12·Node 22(유지보수 종료 약 2027-04, M4 점검 항목)·PostgreSQL 17(DEC-041).
- **호환성(코어 재사용)**: 순수 함수만 재사용(`validator`, `candidates`, `banned_terms`, `limits.evaluate_limits`, `updater.compute_plan_hash` 등). sqlite 의존 모듈(`db.py`, `history.py`, `quota.py`, `live_guard.py`)은 재사용하지 않고 PostgreSQL 기준으로 **재구현**했다 → 로직 이중 유지 부담(RISK-032). 라이브 게이트 14단계 중 `enable_live`·허용 목록·영상 ID 직접 입력은 M3 이식(BE-B 노트 §6).
- **비목표(Non-goals)**: §W4-6 참고.

### W7-3. S-W08(OAuth) 하위 요건 (M2 예정, 축 A SEC-A1~A8 — 새 ID를 만들지 않고 S-W08에 묶는다)
(a) `state` 1회용·10분 이내·서버측 저장소 검증(쿠키 의존 금지: `SameSite=Strict` 쿠키는 구글 콜백에서 안 실릴 수 있음) (b) PKCE S256, `plain` 금지 (c) 리디렉션 URI는 정확히 일치하는 단일 값 — 현재 Host 허용 목록에 `127.0.0.1:8080`과 `localhost:8080`이 **둘 다** 있어(`nginx.conf`, `compose.yaml`) 쿠키·CSRF·리디렉션이 호스트별로 갈라진다. M2 전에 안내 주소를 하나로 고정할지 결정(축 D 1-10, Q-W12) (d) `client_secret`은 `api`에만 secrets로 (e) 읽기/쓰기 토큰 분리 저장, 응답 `scope` 검사 (f) `invalid_grant`는 쿼터 소비 없이 `AUTH_EXPIRED` 정지 (g) 콜백(GET)은 S-W03의 문서화된 유일한 예외 (h) 새 토큰 발급 시 이전 refresh token revoke.
