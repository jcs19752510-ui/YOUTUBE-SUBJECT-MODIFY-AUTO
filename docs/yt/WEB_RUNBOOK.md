## 1. 시스템 개요

```
브라우저 ─▶ 127.0.0.1:8080 ─▶ web(nginx: 화면 파일 + /api 전달)
                               └▶ api(FastAPI) ─▶ db(PostgreSQL 17)
                                  worker(같은 이미지, 예약 반영 처리) ─▶ db
                                  migrate(시작 때 1회, 데이터베이스 구조 준비)
```
- 컨테이너(프로그램을 담은 상자) 5개: 상시 4개(`web`, `api`, `worker`, `db`) + 시작 때 한 번 돌고 끝나는 `migrate`. Docker Compose 프로젝트 이름은 `ytweb`.
- 호스트(내 PC)에 열린 포트는 **`127.0.0.1:8080` 하나뿐**. DB(5432)·API(8000)는 밖에서 안 보입니다.
- 네트워크 3개: `front`(web↔api, 외부 통신 불가), `back`(api·worker·migrate↔db, 외부 통신 불가), `edge`(포트 게시용, web만 붙음). web은 DB에 닿지 못합니다. 이 구성은 `web/compose.yaml` 로 확인했고 컨테이너 실측은 7단계 몫입니다.
- 데이터는 Docker 볼륨 3개에 있습니다: `pgdata`(데이터베이스), `backups`(컨테이너 안 백업 작업 공간), `app_secrets`(승인 서명 키). 실제 이름은 프로젝트 접두사가 붙습니다(예: `ytweb_pgdata`) [확인 필요: Windows에서 `docker volume ls`로 확인].
- 호스트 폴더: `web\secrets\`(DB 비밀번호 파일 3개, 처음 `start.ps1` 때 자동 생성, git 제외), `web\backups\`(백업 파일, git 제외).
- 기본은 데모 모드: AI 실서비스 연결 코드는 없습니다(모의 AI). 구글 연결(읽기)·제목 수정(쓰기) 코드는 2026-10-11 에 추가됐고 `google_client.json` 이 있을 때만 켜집니다(15장). 하루 반영 상한 기본 10건, 배치당 최대 50건, 승인 24시간 유효.
- 선택 PIN: 기본 꺼짐. 꺼져 있으면 **이 PC에서 주소를 열 수 있는 누구나** 화면을 사용할 수 있습니다(같은 PC의 다른 프로그램 포함). 데모에서는 영향이 작지만, 실제 연동 전에는 PIN 필수화가 결정 대기 항목입니다.

## 2. 시작·종료·재부팅

### 2-1. 시작
1. Docker Desktop 실행 → 고래 아이콘이 "실행 중"이 될 때까지 대기.
2. `.\web\scripts\start.ps1 -OpenBrowser`
3. 스크립트가 자동으로 하는 일: Docker 확인 → 비밀 파일 생성(처음 한 번, 값은 화면에 안 나옴) → 포트 8080 확인 → 이미지 빌드·시작 → 5개 서비스 준비 대기(기본 최대 300초) → 주소 안내. 첫 실행은 5~15분.
4. "준비 완료!" 가 나오면 성공. 실패하면 문제 서비스의 마지막 로그 25줄이 자동 출력됩니다.
5. `web\secrets\google_client.json` 이 있으면 모든 스크립트가 구글 통신용 설정(`compose.online.yaml`)을 함께 씁니다. 파일이 없으면 쓰지 않습니다(15-1).

### 2-2. 종료
`.\web\scripts\stop.ps1` — 진행 중인 작업을 마무리하느라 최대 1분쯤 걸립니다. 데이터는 보존됩니다. (내부적으로 `docker compose down`, 볼륨 삭제 없음.)
- **배치 진행 중에 PC를 끄거나 종료해도** 이중 반영이 생기지 않도록 설계되어 있고, 다음 시작 때 중간에 멈춘 항목을 확인해 정리합니다. 다만 종료 중 실제 동작은 Windows에서 확인되지 않았습니다 [확인 필요].

### 2-3. 재부팅(PC 껐다 켜기) 후 복구
1. **Docker Desktop은 기본적으로 로그인 때 자동 시작되지 않습니다.** 직접 실행하세요.
2. `.\web\scripts\start.ps1 -NoBuild` (이미지가 남아 있으면 빠릅니다).
3. `.\web\scripts\status.ps1` 로 모두 "정상"인지 확인.
4. 데이터가 남아 있는지 화면(홈 영상 현황)에서 확인.
5. 컨테이너에는 `restart: unless-stopped` 가 있어 Docker가 켜지면 자동으로 올라올 수도 있으나, 실제 동작은 Windows에서 미확인이므로 항상 2~3을 수행하세요.
6. PC가 꺼져 있던 동안 예약된 반영은 **몰아서 실행되지 않고** 켜진 날의 하루 몫만 처리됩니다.

## 3. 상태 점검

`.\web\scripts\status.ps1` 가 보여 주는 것과 정상 기준:
| 점검 | 정상 |
|---|---|
| 서비스 상태 | `db/api/worker/web` = 정상(running + healthy), `migrate` = "마이그레이션 완료"(종료 코드 0) |
| 호스트 포트 | `127.0.0.1:8080->8080/tcp` 하나뿐. `[위험]` 표시가 있으면 즉시 `stop.ps1` 후 로그 확인 |
| 이 PC의 8080 리스너 | 루프백(127.0.0.1)뿐 |
| 응답 확인 | `/api/healthz` → 200 `{"status":"ok"}`, `/api/readyz` → 200 `{"status":"ok","db":"ok","mode":"demo"}` |
| 종료 코드 | 문제 없으면 0, 있으면 1 |
- `readyz` 가 503 `{"status":"degraded","db":"down"}` 이면 DB 문제입니다 → `logs.ps1 -Service db`.
- `readyz` 의 `"mode":"demo"` 는 서버 기본 모드 값(현재 `demo` 로 고정)이며, 실제 수정 모드가 켜져 있어도 `demo` 로 나옵니다. 실제 수정 상태는 화면 맨 위 띠와 홈 카드로 확인하세요.
- 워커의 헬스체크는 **프로세스가 살아 있는지만** 봅니다(실제로 일을 하는지는 모름). 예약 반영이 안 되는 것 같으면 `logs.ps1 -Service worker` 와 화면 홈의 "반영 대기열"을 같이 보세요.
- 화면 쪽 신호: 상단 "서버 연결됨 / 서버 연결 끊김", 홈 "연결 상태".
- 정상 범위(구현 값): 요청 속도 제한 — 앞단 nginx는 주소당 초당 30건(순간 60건까지)·세션 발급은 분당 10건, 프로그램 안에서는 전체 600/분·쓰기 120/분·세션 발급 10/분(모두 임의 기본값). 넘으면 429 `rate_limited`. 요청 본문은 1MB까지. 세션은 처음 연결로부터 최대 12시간, 마지막 사용 후 30분이 지나면 만료(PIN이 꺼져 있으면 화면이 알아서 다시 연결). 속도 목표(SLO)와 복구 목표(RTO/RPO)는 **제안값일 뿐 승인되지 않았고 측정하지 않았습니다**.
- **알림 채널: 없음.** 이메일·문자·푸시 알림이 연결되어 있지 않습니다. 이상은 운영자가 `status.ps1`, 화면 배너, 로그로 직접 확인해야 합니다.

## 4. 로그
- 보기: `.\web\scripts\logs.ps1` (기본 마지막 200줄) / `-Service web|api|worker|migrate|db` / `-Tail 500` / `-Follow` (Ctrl+C로 중단).
- 형식: 앱 로그(`api`/`worker`)는 JSON 한 줄. 접속 기록은 요청 방식·경로·상태·소요시간·요청 번호(`request_id`)만 남고 쿼리·헤더·본문은 남지 않습니다. 화면 서버(`web`, nginx)의 접속 기록도 JSON 한 줄(시각·방식·경로·상태·바이트·소요시간)이며 쿼리 문자열과 쿠키는 기록하지 않고, 오류 로그는 error 수준만 남깁니다(업스트림 오류 줄에는 요청 줄이 남을 수 있음 — 구글 로그인 연동 때 재평가). 비밀번호 등은 마스킹됩니다(패턴 밖 형식은 놓칠 수 있음).
- 보관·회전: 컨테이너마다 10MB × 3개 파일(서비스당 최대 약 30MB)이 차면 오래된 것부터 지워집니다. **`docker compose down` 으로 컨테이너가 다시 만들어지면 컨테이너 로그도 함께 사라집니다** [확인 필요: 실제 확인 안 함 — 문제 조사가 필요하면 종료 전에 로그를 저장하세요: `logs.ps1 -Tail 2000 > 파일`].
- 화면 오류 코드와 로그를 연결하려면 응답 헤더의 `X-Request-Id` 값으로 로그를 검색합니다(개발자 도구가 필요한 고급 작업).
- 문의할 때 로그를 보내기 전에 비밀번호·PIN·개인 정보가 없는지 훑어보세요.

## 5. 백업·복원

### 5-1. 백업 (자동 백업은 없습니다 — 직접 하세요)
- 언제: 데이터를 지키고 싶을 때마다, 특히 **큰 작업(대량 승인·배치 실행) 전후, 코드를 바꿔 다시 빌드하기 전**.
- 명령: `.\web\scripts\backup.ps1` → `web\backups\ytweb-날짜-시각.dump` 와 `.sha256` 파일이 생깁니다. 스크립트가 크기·목차·해시를 확인합니다.
- 포함: 영상·제안·승인·이력·감사 로그. **불포함: DB 비밀번호(`web\secrets`), 승인 서명 키(`app_secrets` 볼륨)**.
- 보관: 암호화 없음, 보관 기간·위치 정책 없음(결정 대기). 중요하면 `web\secrets` 와 함께 별도 안전한 곳(외장 저장장치 등)에 복사하고, 남에게 주지 마세요.
- 백업이 실제로 복원되는지는 한 번 연습해 두세요(5-3).

### 5-2. 복원
1. Docker Desktop 실행, `start.ps1` 로 프로그램 시작(DB가 켜져 있어야 함).
2. `.\web\scripts\restore.ps1 -Latest` 또는 `-File 파일명.dump`
3. `.sha256` 파일이 있으면 해시를 먼저 검사합니다. 다르면 중단됩니다(그 파일은 쓰지 마세요).
4. 경고가 나오면 확인 문구 **`복원합니다`** 를 입력해야 진행됩니다. 현재 데이터는 백업 시점으로 **덮어써집니다**.
5. 복원 전에 현재 데이터를 `pre-restore-*.dump` 로 자동 백업합니다. 복원은 한 번의 트랜잭션이라 실패하면 기존 데이터가 그대로 남습니다.
6. 끝나면 테이블별 행 수가 출력됩니다. 백업 시점과 같은지 확인하세요.
7. 같은 PostgreSQL 메이저 버전(17) 이상으로만 복원하세요.
- **승인 서명 키가 없는 새 환경으로 복원하면 기존 승인은 모두 무효**가 됩니다(안전한 쪽으로 실패). 다시 승인하면 됩니다.
- **새 PC로 옮겨 복원했을 때 실제로 생기는 일은 "기존 승인 무효"입니다.** 감사 기록은 키 없는 해시 연결이라 서명 키가 없어도 검증이 어긋나지 않는 것이 설계입니다(`core/audit.py`, 설계서 `DESIGN.md`의 감사 체인 설명). 예전 안내("무결성 표시가 맞지 않을 수 있다")는 문서 오류였고 `web/README.md` 는 이번에 고쳤습니다. 복원 직후 설정 > 감사 로그의 무결성 표시는 내 PC에서 확인 필요.
- 복원 스크립트는 복원 중 `web`·`api`·`worker` 를 잠시 멈췄다 다시 시작하고(`up -d`), 복원 뒤 감사 로그의 수정·삭제 금지 권한을 다시 확인·회수합니다.

### 5-3. PC 교체·전체 장애 복구 개요

## 10. 장애 대응 순서 (처음 당황했을 때)
1. **멈추고 숨 쉬기.** 데이터가 위험해 보여도 `down -v` 같은 삭제 명령은 절대 입력하지 마세요.
2. `.\web\scripts\status.ps1` — 어느 서비스가 비정상인지 확인.
3. `.\web\scripts\logs.ps1 -Service <그 서비스>` — 마지막 줄들의 오류 확인.
4. 흔한 원인과 조치
   | 증상 | 조치 |
   |---|---|
   | Docker 엔진 연결 불가 | Docker Desktop 실행·1~2분 대기, 안 되면 `wsl --update` 후 PC 재시작 |
   | 포트 8080 사용 중 | `Get-NetTCPConnection -LocalPort 8080 -State Listen` 으로 `OwningProcess` 확인 후 해당 프로그램 종료 |
   | `migrate` 실패 | 로그 확인. api/worker는 `migrate` 가 성공해야 시작합니다 |
   | 컨테이너 계속 재시작 | 해당 서비스 로그 확인, 메모리 부족이면 Docker Desktop 설정 > Resources 확인 |
   | 비밀 파일 없음 + DB 볼륨 있음 | `web\secrets` 를 되돌려 놓기(백업해 둔 폴더). 없으면 데이터 접속 불가 — 개발 담당 상의 |
   | 화면 하얌 | 브라우저 F12 콘솔의 CSP 오류 확인 |
5. 해결되면 `status.ps1` 로 재확인, 그래도 안 되면 `stop.ps1` → `start.ps1`(`down -v` 아님).
6. 조치 전 `backup.ps1` 가 가능하면 먼저 실행(DB가 healthy일 때).
7. 에스컬레이션: 담당자·연락처·응답 시간은 **미정**입니다(결정 필요). 임시로는 개발 담당(이 저장소의 작업 담당)에게 증상, 오류 코드, `status.ps1` 출력, 관련 로그를 전달합니다.
- **DB 재시작·연결 끊김**(8단계 결함 조치 반영): 워커가 반영하는 도중 DB 연결이 잠깐 끊기면, 아직 유튜브에 쓰기 전인 항목은 "실패"로 닫히지 않고 **"대기"로 돌아가 다음 차례(워커 틱)에 다시 처리**됩니다. 따라서 DB를 `restart` 한 뒤에는 `status.ps1` 로 정상 확인 후 배치 상세에서 대기 건수가 줄어드는지 보면 되고, 같은 항목을 수동으로 다시 만들 필요는 없습니다. 이미 유튜브에 쓰기 시작한 뒤의 끊김은 아래 "예정" 기록 규칙을 따릅니다(자동 정리 없음). 코드와 클라우드 시험 기준이며 Windows PC 실측은 아닙니다.
- 반영 도중 중지·실패·재시작이 있었을 때: 이력에서 항목별 결과를 확인하세요. "건너뜀"은 안 바뀐 것, `result_unknown`은 바뀌었을 수도 있어 확인 필요, "예정(planned)" 기록이 남으면 그 영상은 새 반영이 막힙니다(자동 정리 없음, 알려진 제한).

## 11. 보안 사고가 의심될 때
1. 탐지 신호: 감사 로그의 낯선 `session.denied`/`session.create` 반복, 무결성 경고, `status.ps1` 의 `[위험]`(8080이 127.0.0.1 외 주소에 열림), 기억에 없는 승인·배치.
2. 격리: `.\web\scripts\stop.ps1` 로 종료(데이터 보존). 필요하면 Wi-Fi 연결을 끊어 PC를 외부와 분리.
3. 보존: 종료 전 `logs.ps1 -Tail 2000` 저장, `backup.ps1` (가능하면). 증거를 지우는 `reset-demo.ps1` 은 쓰지 마세요.
4. 통지·법적 확인: 개인정보 유출 가능성이 있으면 법적 통지 의무 여부를 **사용자(소유자)가 직접 확인**해야 합니다. 이 문서·에이전트는 판단하지 않습니다. 현재 데모 모드는 가짜 데이터만 다루고 승인자 이름 외 개인정보를 수집하지 않습니다.
5. 복구: 원인 확인 후 `start.ps1`, 필요하면 `restore.ps1`. 비밀번호 파일 유출이 의심되면 8장의 교체 절차(미검증)를 개발 담당과 진행.
6. 사후: 포스트모템을 작성합니다(양식 `templates/postmortem-template.md`).

## 12. 서비스 종료·폐기 절차 (개요, 실제 실행은 소유자 별도 승인)
1. 사용자 고지: 현재 사용자는 소유자 1인. 다른 사람이 쓰고 있다면 사전에 알립니다.
2. 보존 여부 결정: 필요한 이력은 `backup.ps1` 로 백업하고 CSV 내보내기(성과 리포트). 법적 보존 의무가 있는지는 소유자가 확인합니다 [확인 필요].
3. 종료: `stop.ps1`.
4. 파기(되돌릴 수 없음, 별도 승인 후): `reset-demo.ps1 -DeleteVolumes`, `web\backups`·`web\secrets` 폴더 삭제(복구 불가능하게 지울 방법은 별도 확인), Docker 이미지 정리, Docker Desktop 제거 여부 결정.
5. 계정·키 회수: 현재 데모에는 구글·AI 키가 없습니다. 실제 연동을 한 뒤에는 구글 계정에서 앱 접근 권한 해제, AI 서비스 키 폐기가 추가됩니다.

## 13. 알려진 제한·기술부채 (인수인계 필수 인지)

### 13-2. 보안 결정: 데모 모드 한정으로 그대로 두기로 한 3가지와 선생님이 지금 할 일

#### 13-2-1. 프로그램 안의 컨테이너가 이 PC에서 열려 있는 다른 서비스에 닿을 수 있음 (보고서 항목 9-011)

- **Windows Docker Desktop에서의 실제 동작은 사용자 PC 실측이 필요합니다.** Docker Desktop은 Linux 가상 머신 안에서 돌아서 결과가 다를 수 있고(더 막혀 있을 수도, 아닐 수도 있음), 클라우드에서는 확인할 수 없었습니다. 10단계(선생님 PC 구동 검증) 때 개발 담당이 확인합니다.

PowerShell에서 `Get-NetTCPConnection -State Listen | Where-Object { $_.LocalAddress -in '0.0.0.0','::' } | Sort-Object LocalPort | Format-Table LocalAddress,LocalPort,OwningProcess` (이 명령은 Windows에서 실행해 확인하지 못했습니다 — 내 PC에서 확인 필요). 8080(이 프로그램은 127.0.0.1에만 열림)을 뺀 목록에서 모르는 프로그램이 있으면 `Get-Process -Id 번호` 로 이름을 보고, 필요 없으면 끄거나 알려 주세요.

#### 13-2-2. 감사 로그가 "DB 관리자 계정이 기록을 고치고 다시 계산"하는 것은 알아채지 못함 (보고서 항목 9-014)
- **무엇이 위험한가**: 감사 로그(누가 언제 무엇을 승인·변경했는지)는 기록마다 앞 기록의 해시(지문)가 이어져 있어, 중간 기록을 고치거나 지우면 화면의 검사가 알아챕니다. 하지만 **지문 계산에 비밀 키가 쓰이지 않아서**, DB 관리자(소유자) 비밀번호를 가진 사람이 기록을 고친 뒤 지문을 처음부터 다시 계산(재계산)하면 알아채지 못하고, 맨 마지막 몇 건을 통째로 지워도 알아채지 못합니다. 또 앱 계정이 감사 로그 외의 표(변경 이력·승인 등)는 수정할 수 있습니다(앱이 해킹당한 경우).
- **왜 지금은 그대로 두는가**: DB 관리자 비밀번호는 이 PC의 `web\secrets` 폴더에 있어, 그것을 가진 사람은 이미 이 PC를 장악한 것입니다. 한 사람이 혼자 쓰는 데모에서는 감수할 수 있는 수준으로 판단했습니다.
- **선생님이 지금 할 일**: 필수는 없습니다. `web\secrets` 폴더를 남에게 보내거나 공유 폴더에 두지 마세요. (선택) 중요한 작업을 한 날에는 감사 로그의 마지막 기록 건수를 메모해 두면 나중에 맨 끝이 지워졌는지 눈으로 비교할 수 있습니다.
- 다시 판단하는 때: **실제 구글에 연결하기 전**, **다중 사용자**가 생길 때, **외부 접속**을 허용할 때. 해결 방법 후보는 비밀 키를 쓰는 지문(HMAC) 또는 마지막 지문을 다른 곳에 따로 보관하는 것입니다.

#### 13-2-3. 데이터 보관 기간·삭제·백업 암호화가 아직 없음 (보고서 항목 9-013)

## 15. 구글 연결·실제 제목 수정 운영 (M2·M3, 2026-10-11 추가)

> **상태 정직 표기**: 이 장은 코드(`google_oauth.py`, `live_read.py`, `live_write.py`, `live_gateway.py`, `routers/google.py`)와 가짜 구글 자동 시험(백엔드 시험 파일 6개, 화면 시험 `google.test.tsx`)에 근거합니다. **실제 구글 서버 접속, 실제 채널 영상 읽기, 실제 제목 변경은 한 번도 하지 않았습니다.** 15장의 절차 중 Windows·실제 구글이 필요한 부분은 모두 미검증입니다. 이 단계(11단계)에서는 새로 검증하지 않고 코드·결과서를 요약했습니다.

### 15-1. 구성과 켜는 조건
- **구글과 통신하는 컨테이너**: `web\secrets\google_client.json` 이 있을 때만 `api`·`worker` 가 `egress` 네트워크에 붙습니다(`compose.online.yaml`). `db`·`web` 은 붙지 않습니다. 파일이 없으면 외부 통신 없는 M1 상태 그대로입니다. `start.ps1`·`stop.ps1` 등 모든 스크립트가 같은 규칙으로 compose 를 부릅니다(`_common.ps1`의 `Invoke-Compose`).
- **게이트웨이 선택 3조건**(모두 맞아야 실제 쓰기, 아니면 모의): ① `YTWEB_LIVE_WRITE=1` ② 쓰기 토큰 연결 ③ `YTWEB_LIVE_ALLOWED_VIDEOS` 에 영상 ID 1개 이상.
- **켜는 방법**: 구글 연결(읽기)과 [제목 수정 권한 연결]을 한 뒤, `web\.env.example` 을 `web\.env` 로 복사해 `YTWEB_LIVE_WRITE=1`, `YTWEB_LIVE_ALLOWED_VIDEOS=영상ID(쉼표로 구분)` 로 고치고 `start.ps1` 을 다시 실행합니다(`compose.online.yaml` 이 api·worker 에 두 값을 전달합니다. 기본은 0과 빈 값). 자세한 순서는 `WEB_INSTALL.md` 8-4. 코드 확인까지만 했고 Windows PC 에서 실제로 해 본 적은 없습니다 [확인 필요]. 구글 연결 파일이 없으면 이 값은 전달되지 않습니다.
- **끄는 방법**: ① 가장 빠른 방법(코드로 확인) 화면 [연결 해제]는 읽기·쓰기 토큰 파일을 모두 삭제하므로 3조건 중 ②가 깨져 즉시 모의 게이트웨이로 돌아갑니다(`routers/google.py` disconnect, 자동 시험으로 확인). 이미 큐에 있는 반영 작업이 있어도 워커가 같은 선택 규칙을 쓰므로 토큰이 없으면 실제 쓰기를 하지 않는 구조입니다(코드 읽기 기준, 실행 확인 아님). ② `web\.env` 에서 `YTWEB_LIVE_WRITE=0` 으로 고치거나 허용 영상을 비우고 `start.ps1` 을 다시 실행. 도중에 모드가 바뀌면 확정해 둔 배치 항목은 `live_mode_changed` 로 건너뛰고(아무것도 바뀌지 않음), 반영 때와 모드가 다른 롤백은 `live_mode_mismatch` 로 거부됩니다.
- **허용 목록 안전장치**: 실제 모드에서 허용 외 영상은 ① 초안/사전 점검 ② 반영 직전(변경 기록·쿼터 확정 전) ③ 롤백에서 `live_not_allowed` 로 막힙니다. 게이트웨이 자체도 같은 목록을 한 번 더 검사해, 어긋나면 네트워크 호출 전에 거부합니다. 목록은 설정 API로 바꿀 수 없습니다.
- **모호 응답**: 구글 응답이 끊기거나 새 제목이 확인되지 않으면(`definite=false`) 한 번 재조회하고, 확인이 안 되면 `planned`(예정) 기록을 남긴 채 `result_unknown` 으로 중단합니다. 자동 정리·자동 재시도로 이중 반영하지 않는 구조입니다.

### 15-2. 토큰 파일 폐기·재발급 (google_write_token.json 포함)
| 상황 | 절차 | 근거·상태 |
|---|---|---|
| 정상적으로 쓰기 권한을 끊고 싶다 | 화면 홈 카드 [연결 해제] → [해제] (읽기·쓰기 토큰 둘 다 삭제, 감사 로그 `google.disconnected` 기록) | 자동 시험으로 확인. Windows 실제 클릭 미확인 |
| 쓰기 권한만 다시 받고 싶다(만료 등) | 홈 카드 [제목 수정 권한 연결]을 다시 누르고 구글에서 허용 → 새 `google_write_token.json` 으로 교체(임시 파일에 쓴 뒤 교체) | 코드 확인. 실제 구글 미확인 |
| 읽기만 다시 | [구글 계정 연결] 재실행 | 위와 같음 |

- 토큰 파일은 컨테이너 볼륨(`app_secrets`) 안에 있어 호스트 폴더에서 직접 보이지 않습니다. 파일을 수동으로 지우는 절차는 만들지 않았고, 화면 [연결 해제]만 공식 방법입니다.
- 백업(`backup.ps1`)에는 토큰이 포함되지 않습니다. PC 교체·복원 후에는 구글에 다시 연결해야 합니다.
- 토큰 파일은 암호화되지 않은 JSON(0600)입니다. 로그·화면·주소·감사 로그에 토큰을 싣지 않는 구조이나(자동 시험으로 확인), 볼륨을 읽을 수 있는 사람은 토큰을 읽을 수 있습니다 — 잔여 위험(`docs/yt/threat_model.md` 의 구글 연결 관련 항목 참고).

### 15-3. 실제 변경이 의심될 때 점검 순서

3. **누가/언제 했나**: 설정 > 감사 로그에서 `google.connect_write.start`, `google.write_connected`, `batch.*`, `change.apply`, `change.rollback`, `google.disconnected` 순서를 확인합니다. 무결성 표시도 확인(한계는 7장).
4. **허용 목록 밖 영상이 바뀌었나**: 설계상 불가능해야 합니다. 바뀌었다면 즉시 보안 사고(11장)로 처리하고 이력·감사 로그 화면 캡처와 `logs.ps1 -Service api -Tail 2000`, `-Service worker` 를 저장하세요. 개발 담당에게 `live_gateway.py`·`live_write.py` 점검을 요청합니다.
5. **결과를 모르는 항목(`result_unknown`, "예정" 상태)**: 유튜브 Studio 에서 현재 제목을 직접 확인한 뒤 판단합니다. 바뀌었으면 이력에서 롤백, 아니면 개발 담당에게 전달. 확인 전에는 같은 배치를 다시 실행하지 마세요.
6. **되돌리기**: 이력·롤백 화면(영상 ID를 직접 입력해 확인). 쉬운 말로: 반영 뒤에 선생님이 유튜브에서 그 영상을 또 고쳤다면 프로그램이 "자동으로 되돌리지 않았습니다"(409)라고 거부하는 것이 정상입니다. 허용 목록에서 빠진 영상은 롤백이 `live_not_allowed` 로 막히니 Studio 에서 직접 고칩니다. 실제 수정 모드의 롤백은 반영 뒤 유튜브에서 제목·설명·태그·카테고리·언어가 바뀌었으면 `live_changed_since_apply` 로 거부됩니다(덮어쓰지 않는 보수적 기본값). 이 경우에도 Studio 에서 직접 확인해 고칩니다.

### 15-4. 쿼터(사용량)
- 구글 YouTube Data API 기본 하루 쿼터 10,000단위(`WEB_LEGAL_NOTICE.md` 참조, 구글 공식 값은 실제 콘솔에서 확인 필요). 프로그램의 하루 상한은 기본 6,000단위(60%)로 홈에 표시됩니다.

- 초과하면 `quota_exceeded`/`quota_exhausted` 로 중단되고 미국 태평양 시간 자정 이후 다시 시도합니다. 실제 소진 시 동작은 실제 구글에서 확인하지 못했습니다.
