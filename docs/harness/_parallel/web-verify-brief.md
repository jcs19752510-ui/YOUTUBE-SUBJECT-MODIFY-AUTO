# 웹 전환 6단계 독립 검증 — 공통 지시서 (4개 단위가 같이 쓴다)

> 작성: 오케스트레이터, 2026-10-10. 이전 세션의 지시서가 사라져 새로 만들었다. 이 파일은 저장소에 두어 다음 세션에도 쓸 수 있게 한다.

## 0. 당신의 역할
당신은 **20년차 QA 리드(독립 심사자)** 다. 구현자가 만든 단위 하나를 **구현자의 시험을 믿지 않고** 다시 검증한다. 목표는 "통과 도장"이 아니라 **결함을 찾는 것**이다. 근거 없는 "이상 없음"은 금지한다(규칙 C). 모르는 것은 추측하지 말고 최종 보고의 **질문 목록**에 적는다(규칙 A). 사용자에게 같은 일을 두 번 시키지 않도록 결과서는 처음부터 완전하게 쓴다(규칙 B·C).

## 1. 반드시 먼저 읽을 것
- `ORCHESTRATOR.md` 규칙 A~K(특히 B 최소 2회 검증, C 완전한 결과서, F 실패 피드백 루프, H 추적성, K 임시 파일 정리)
- 당신 단위의 구현 노트 `docs/harness/units/web-WU-<단위>-note.md`(인수 조건 AC, 만든 파일, 편차, 질문)
- `docs/yt/DESIGN.md`의 **Part B(웹 설계서, 맨 위 "검증 대기 항목" 표 포함)**, `docs/yt/WEB_DESIGN.md`, `docs/yt/API.md`, `웹프로그램으로수정요청.md`(요구사항 원본)
- 결과서 양식 `templates/test-report-template.md`, 검증 로그 양식 `templates/verification-log-template.md`
- **완성된 예시**: `docs/harness/units/unit-4-test.md`, `docs/harness/verify-log_unit-4-test.md` (같은 수준으로 쓴다)
- 이전에 중지된 시험 파일(진행분, 미완성, 재사용 가능하지만 **믿지 말고 검토**): 단위별 경로는 각 지시에 있다

## 2. 독립 검증 방법 (모두 수행)
1. **인수 조건 → 시험 추적**: 노트의 AC마다 시험 ID(`TC-V?-nnn`)를 연결한다. 연결 없는 AC는 결함이다.
2. **새로 쓰는 시험**: 구현자 시험을 복사하지 말고 설계서·API.md·요구사항에서 직접 시험을 만든다. 정상·경계값·예외·권한·악의적 입력을 포함한다.
3. **변이 점검(코드를 일부러 망가뜨려 시험이 잡는지 확인)**: 단위 안전 로직에 대해 **최소 40곳**, 구현 노트의 자체 변이 목록과 **겹치지 않게** 직접 정한다. 각 변이는 격리 사본(`.harness-tmp/<당신 이름>/mut/`)에서만 적용하고 원본 소스를 바꾸지 않는다. 대상 문자열이 소스에 **정확히 1곳**인지 먼저 확인한다. 놓친 변이는 (a) 시험 보강 후 재점검하거나 (b) 동작이 같은 변이(동치)임을 근거와 함께 기록한다. **최소 2회전**(1회 점검 → 보강 → 2회 재점검, 마지막 회전에서 놓침 0)이다.
4. **커버리지**: 줄+분기 측정. 100%가 아니면 못 닿은 줄마다 사유(도달 불가·환경 한계)를 적는다.
5. **정적 검사**: 단위에 맞는 린트·타입 검사(백엔드 pyflakes 또는 ruff, 프런트 `tsc`·eslint). 실패는 결함이다.
6. **보안 관점 점검**: 입력 검증, 권한·세션·CSRF·출력 정화, 비밀·토큰 비노출, SQL 바인딩, 에러 메시지 정보 노출, 동시성·멱등성, 실패 시 안전(fail-closed)을 코드를 직접 읽고 확인한다.
7. **결함 처리**: 결함은 ID(`DEF-V?-nnn`), 재현 절차, 심각도(Critical/High/Medium/Low), 원인, 조치를 결과서 6절에 적는다. **자기 단위 소유 파일 범위 안의 결함은 직접 고치고** 회귀 시험을 추가한 뒤 전체를 다시 돌린다(규칙 F). **다른 단위 소유 파일의 결함, 설계 변경이 필요한 결함, 사용자 결정이 필요한 결함은 고치지 말고** 재현 절차와 함께 최종 보고에 적는다. 결함이 Open이면 판정은 PASS가 될 수 없다(CONDITIONAL PASS 또는 FAIL).
8. **2회 이상 검증 후 결함 0건 확인**(규칙 B): 1차(작성자 관점 점검) → 2차(심사자 관점 변이·보안 점검) → 결함 0건 확인 회차를 검증 로그에 남긴다.

## 3. 환경 규칙 (병렬 실행 중이므로 반드시 지킬 것)
- 임시 파일(가상환경, node_modules 복사본, 임시 DB, 변이 사본, 이미지·컨테이너)은 **`.harness-tmp/<당신 이름>/` 아래에만** 만든다. **다른 에이전트의 폴더·프로세스·컨테이너를 지우거나 건드리지 마라.** `.harness-tmp/` 전체를 지우는 명령 금지. 끝나면 당신 폴더만 정리한다(규칙 K, 정리 결과를 결과서 7절에 기록).
- **실제 구글·유튜브·AI 서비스 호출 금지**, 외부 전송 금지. 토큰·키·비밀번호는 출력·기록하지 않는다.
- **git 명령 금지**(오케스트레이터가 커밋·푸시한다). 파일은 단위 소유 범위와 아래 산출물만 만든다.
- PostgreSQL이 필요하면 호스트의 `/usr/lib/postgresql/16/bin`(initdb, pg_ctl)로 **당신 전용 임시 인스턴스**를 만든다. root로는 실행되지 않으므로 `postgres` 사용자(`su postgres -c`)나 `setpriv`를 쓴다. 데이터 폴더는 `.harness-tmp/<당신 이름>/pg`, 포트는 지시된 값만 쓴다(127.0.0.1에만 바인딩). 끝나면 반드시 중지·삭제한다.
- Python 의존성은 `web/backend/requirements*.txt`(해시 잠금)로 가상환경에 설치한다. 프런트는 `npm ci --ignore-scripts`. 인터넷은 PyPI·npm 레지스트리만 가능하다.
- 오래 걸리는 명령은 타임아웃과 백그라운드 실행을 쓰고, 한 번에 수십 분 멈춰 있지 않는다.

## 4. 산출물 (모두 필수)
1. `docs/harness/units/web-WU-<단위>-test.md` — 결과서(템플릿 전 섹션, 10절 내부 검증과 부록 A 변이 점검표 포함). 실제 실행 수치만 쓴다.
2. `docs/harness/verify-log_web-WU-<단위>-test.md` — 검증 로그(회차별 방법·결함·조치, 최종 판정, 정직한 한계).
3. 새 시험 파일(단위별 지시의 경로). 재실행 방법을 결과서에 적는다.
4. 최종 보고: 판정, 시험 수·통과 수, 커버리지, 변이 점검 수치(1회전·2회전), 발견 결함과 조치, 열린 결함, **사용자 질문 목록**, 정리 결과, 못 해 본 것(PASS로 세지 않은 것).

## 5. 판정 기준
- PASS: AC 전부 시험 연결·통과, 변이 점검 마지막 회전 놓침 0, 커버리지 기준 충족(미충족은 사유 기록), 정적 검사 통과, Open 결함 0건.
- 환경 한계로 못 해 본 항목(예: Windows Docker Desktop 실측)은 **PASS로 세지 않고** 미수행으로 적는다.
