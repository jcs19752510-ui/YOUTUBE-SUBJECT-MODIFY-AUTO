# unit-4 구현 노트 — WU-4 변경 계획·교체 제한·이력·롤백 (5단계)

- 작업 단위: **WU-4** (feature F-C 수정·이력·롤백) / **속도 트랙: L5(안전 핵심)** / Tier: Standard / 선행: WU-2, WU-3(완료)
- 파일 범위: `src/ytitle/{updater,limits,history}.py`, `src/ytitle/commands/{plan,rollback}.py`, `tests/test_{updater,limits,history,plan_cmd,rollback_cmd}.py`, `tests/wu4_support.py`(테스트 공용 도우미, 테스트 파일 아님), 이 노트. 범위 밖 수정 없음, 신규 의존성 없음.
- **이 단위에는 YouTube 쓰기 호출도, 구글/네트워크 import도 없다.** 쓰기 자리는 `UpdateGateway`(Protocol, 구현 없음)와 항상 거부하는 `execute_update`뿐이다(SEC-001).

## 1. 구현 범위
- `limits.py`: 교체 제한 4종(최소 간격 72h, 영상별 변경 횟수 3, 재변경 시 최소 노출수 1000, 하루 적용 건수 3)을 **사실 수집(`gather_facts`, DB 읽기 전용) + 순수 판정(`evaluate_limits`)**으로 분리. 노출수를 모르면 거부(사유와 해결 방법 안내). 값은 모두 `Settings`(DESIGN 5-3 `cadence`).
- `updater.py`: canonical JSON·`snippet_hash`·`compute_plan_hash`, 새 제목 최소 규격 재검사, 저장 snippet 파싱, 요청 본문(`build_update_body`: snippet 깊은 복사 + 제목만 교체), `create_plan`(후보·영상·제한·쿼터 종합, 읽기 전용), 순차 교체 모드 제외 영상군 판정.
- `history.py`: 후보 상태 머신(DESIGN 3-2의 7개 간선만 허용), `begin_change`(planned 행 + 백업 snippet 전체, 승인 필수), `finish_change`(이력 행 갱신과 후보 전이를 한 트랜잭션으로), `record_aborted`, 조회, **롤백 계획(`plan_rollback`)과 롤백 DB 처리(`begin_rollback` → `finish_change`)**.
- `commands/plan.py`: `plan --candidate N` (SCR-003). `commands/rollback.py`: `rollback --change N [--live]` — 계획 출력만, `--live`는 '아직 활성화되지 않았습니다'로 거부(종료 코드 3).

## 2. 설계서 대비 편차와 사유
| # | 편차 | 사유 |
|---|---|---|
| 1 | `plan_hash` 입력에 설계서의 5개 항목(영상 ID·후보 ID·이전 제목·새 제목·snippet 해시) 외에 **`v`(규격 버전 1)·`kind`(apply/rollback)·`change_id`(롤백만)**를 더함. JSON은 키 정렬·공백 없음·한글 그대로(UTF-8)이고 SHA-256 | 적용용 해시가 롤백 계획에 재사용되거나 규격이 몰래 바뀌는 것을 막기 위해. **WU-5는 6단계에서 재조회한 snippet으로 `updater.compute_plan_hash`를 그대로 호출해 비교해야 한다**(규격은 TC-423이 고정). |
| 2 | 교체 제한 결과를 표가 아니라 `[통과]/[차단] 항목: 내용` **한 줄씩** 출력 | 표 셀이 80열에 맞춰 잘리며 '가능한 시각' 같은 핵심 문구가 사라지는 것을 테스트가 발견(TC-505). `--plain`에서도 같은 형식. |
| 3 | **'변경'으로 세는 행 = `result`가 `success` 또는 `planned`**. `failed`·`aborted`는 세지 않음. `planned`(호출 직전 기록 후 결과 미확정)는 실제로 제목이 바뀌었는지 알 수 없어 보수적으로 변경으로 간주. 간격·횟수는 적용/롤백 구분 없이 같은 영상의 모든 변경을 센다 | 설계에 정의가 없어 fail-closed로 정함. **부작용**: 비정상 종료로 `planned`가 남으면 그 영상은 계속 막힌다(질문 3). |
| 4 | **하루 = 태평양 시간 날짜**(쿼터와 같은 경계, 서머타임 전환일 포함). 하루 상한은 `change_type='apply'`이고 success/planned인 전체 영상의 행을 센다 | 설계서가 '하루'의 기준 시간대를 정하지 않아 기존 규약(ADR-006)을 따름. |
| 5 | **노출수 기준**: 직전 변경 이후 `after`/`periodic` 단계 지표 중 **기간 시작일이 변경 시각의 UTC 날짜보다 뒤**이고 변경 이후에 가져온 것의 **최댓값**. 시작일이 없는(CSV 등)·`NULL`인 지표는 제외. 첫 변경에는 적용하지 않음. 임계값 0이면 조건 꺼짐 | 변경 이전 시간이 섞인 기간을 확실히 배제(보수적). 따라서 변경 당일에 시작하는 기간은 인정되지 않으며, 변경 다음 날 이후 시작하는 기간의 지표를 가져와야 통과한다. |
| 6 | **롤백에는 교체 제한을 적용하지 않음**(72h·횟수·노출수·하루 상한) | 사고 복구가 제한 때문에 막히면 안 된다는 판단. 대신 '그 영상의 가장 최근 변경'일 때만 롤백 가능(질문 1). |
| 7 | 롤백 계획: 원래 제목은 **백업 snippet**에서, 본문은 **지금 저장된 snippet 전체 + 제목만 원래 제목**으로 만든다. 적용 이후 제목 외 항목이 바뀌었으면 `[주의]`로 알림 | 백업 snippet 전체를 되돌리면 적용 후 사람이 Studio에서 고친 설명·태그를 덮어쓸 수 있음(T-15). 실제 호출 시 WU-5가 재조회한 최신 snippet으로 같은 방식으로 다시 만들어야 한다. |
| 8 | 롤백은 `apply`이면서 `success`인 변경, 백업이 읽히고 이력의 이전 제목과 일치, **같은 영상에 이후 변경(success/planned)이 없을 때만** 가능. 이중 롤백도 이 규칙으로 막힘 | 오래된 제목으로 최신 제목을 덮는 사고 방지. |
| 9 | 순차 교체 모드의 제외 영상군(비공개·아동용·예약 라이브/프리미어·Shorts ≤180초, 모르는 값은 제외 쪽)은 **`sequential_mode.enabled=true`일 때만 계획을 거부**. 꺼져 있으면 `[주의]`로만 알림 | DESIGN 8-4('순차 교체 모드에서만 제외 근거로 사용')와, 첫 실제 적용 대상이 비공개 테스트 영상(SEC-012)이라는 점을 함께 만족시키는 해석(질문 5). |
| 10 | `plan`은 `approved` 상태 후보도 허용(계획 확인용). `blocked`·미검증·`applied`/`evaluated`/`rolled_back`은 `SafetyGateError`(종료 코드 3). 교체 제한/쿼터 부족은 화면을 모두 출력한 뒤 종료 코드 3 | 설계에 종료 코드 규정이 '안전 게이트로 중단=3'뿐이라 그에 맞춤. |
| 11 | 쿼터 필요량 = `update_cost + 2 × read_cost`(기본 52), 여유분 없음. `plan`은 쿼터를 **예약하지 않고** 남은 양만 읽는다 | 설계의 '읽기 2 + 쓰기 50 + 여유'에서 여유 값이 정의되지 않음. dry-run이 쿼터를 소모하지 않게. |
| 12 | `begin_change`가 승인(후보 `approved`, 승인자·승인 시각)·계획 해시 재계산·**교체 제한 재검사**를 직접 수행하고 하나라도 어긋나면 아무것도 쓰지 않음. `begin_rollback`은 영상 ID 직접 입력 값과 해시·이후 변경 여부를 재확인 | 승인 없는 이력/상태 변경을 모듈 수준에서 불가능하게(WU-5의 게이트와 별개의 두 번째 방어선). |
| 13 | `plan`에 검증 이후 금칙어 사전이 바뀌었는지(해시 비교) `[주의]` 표시 추가 | SEC-017의 '사전이 바뀐 사실 표시'를 plan에서도 놓치지 않기 위해. |
| 14 | `rollback --live`는 `SafetyGateError`로 거부하지만 `cli.py`가 `run_logs.mode`를 `live`로 기록한다 | `cli.py`는 WU-0 소유. 쓰기는 일어나지 않았음(TC-521). |

## 4. 수동 확인이 필요한 부분
- **실제 YouTube를 호출하지 않았다.** `videos.list`의 snippet은 `thumbnails`·`publishedAt`·`channelId` 등 **읽기 전용 필드**를 포함한다. 요구(전체 snippet 보존)대로 이를 그대로 본문에 넣지만, **API가 이 본문을 수락하는지·읽기 전용 필드를 무시하는지는 미확인 [확인 필요]**. 12단계 비공개 테스트 영상에서 확인하고, 거부되면 `build_update_body`에서 쓰기 가능 필드만 남기도록 조정해야 한다(TC-426이 보존 범위를 고정하고 있어 함께 수정).
- `fetch --metrics --phase after`로 가져온 지표의 기간 시작일 형식(`YYYY-MM-DD`)과 노출수 열이 실제 응답에서 채워지는지(WU-2 노트 4절의 미확인 사항과 동일). 채워지지 않으면 재변경은 항상 거부된다(설계 의도).
- Windows 콘솔에서 한글 줄 길이/줄바꿈 표시(이 환경은 Linux). 제한 결과가 표가 아니라 긴 줄이라 80열에서 줄바꿈된다.
- 하루 상한·간격 등의 수치는 임의 기본값(02 가정 4)이며 사용자 확정 전.

**질문**(진행을 막지 않음)
1. 롤백에 교체 제한(특히 하루 상한 SEC-020)을 적용할지: 현재는 사고 복구가 막히지 않도록 **면제**했다. 면제 대신 '롤백도 하루 N건'을 원하면 `limits`에 `change_type` 인자를 추가하면 된다.
2. 사후 검증(SEC-010, 설계 5-2 14단계)이 실패한 적용의 `title_changes.result`를 무엇으로 기록할지: 제목이 실제로 바뀌었으므로 **`success` + `verify_result_json.ok=false`**를 권장한다(롤백은 `success`인 적용만 대상). `failed`로 기록하면 롤백 명령이 거부되고 교체 제한에서도 빠진다. WU-5 설계에서 확정 필요.
3. 비정상 종료로 남은 `planned` 행의 정리 방법: 현재는 계속 '변경'으로 세어 그 영상을 막고(보수적) 해제 수단이 없다. WU-5의 시작 시점 점검(오래된 `planned`를 사람 확인 후 `aborted`로 전환)이나 `purge`와의 관계 결정이 필요하다.
4. 읽기 전용 필드를 포함한 snippet 전체를 `videos.update`에 보내도 되는지(4절): 12단계 전에 확인할 방법(공식 문서 재확인 또는 비공개 테스트 영상)을 정해 주세요.
5. 순차 교체 모드 제외 영상군(POL-003)을 모드가 꺼져 있을 때도 거부해야 하는지: 현재는 켜졌을 때만 거부(비공개 테스트 영상 첫 적용 때문). 항상 거부로 바꾸면 SEC-012의 첫 적용 절차와 충돌한다.
6. WU-3의 `validate`는 재검증 시 `blocked`↔`filtered`를 직접 UPDATE한다(설계 3-2는 `blocked`를 종료 상태로 규정). `history.ALLOWED_TRANSITIONS`는 설계대로 `blocked`를 종료로 두었으므로 두 모듈의 규칙이 다르다. 사전 변경 후 재검증으로 `blocked` 후보를 되살리는 것을 허용할지 결정 필요.
7. `docs/yt/04_ux_design.md` SCR-003의 '교체 제한 위반(사유와 가능한 시각)'을 표가 아닌 줄 단위로 구현했다(편차 2). UX 문서에 반영할지 확인.
