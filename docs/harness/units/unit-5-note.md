# unit-5 구현 노트 — WU-5 승인·안전 게이트·실제 쓰기·롤백 활성화 (5단계)

- 작업 단위: **WU-5** (feature F-C) / **속도 트랙: L5(프로젝트에서 가장 위험한 부분: 실제 쓰기 경로)** / Tier: Standard / 선행: WU-4(완료)
- 파일 범위: `src/ytitle/{approvals,live_guard}.py`, `src/ytitle/commands/{apply,approve}.py`, `src/ytitle/commands/rollback.py`(`--live` 스텁 교체), `tests/test_{approvals,live_guard,apply_cmd,approve_cmd}.py`, `tests/wu5_support.py`(공용 도우미), `tests/test_rollback_cmd.py`(TC-521·TC-526 변경, TC-983~985 추가), 이 노트. 신규 의존성 없음. cli.py·config.py·db.py·updater.py 등은 수정하지 않았다.
- **실제 구글 호출 없음**: 모든 테스트는 가짜 서비스 객체만 쓰고, 소켓 `connect`와 `googleapiclient.discovery.build`를 막은 채 실행한다.

## 1. 구현 범위
- `approvals.py`: 승인 파일 생성/읽기/검증/소진. `plan_hash`(WU-4 `compute_plan_hash`) 바인딩, 만료(설정 `approval.ttl_hours` 이하), 1회용(`used`), 위조 방지(HMAC-SHA256 `mac`, 키는 토큰 폴더), 파일 위치 제한(영상 ID 정규식·정수 후보 번호·심볼릭 링크 거부·8KB 상한·정확한 키 집합).
- `live_guard.py`: DESIGN 5-2의 **14단계 fail-closed 게이트**를 문서 순서대로 구현(`_g1`~`_g10` → `_step11` → `_send_with_retry`/`_send_update` → `_verify_and_record`). 적용(`apply_live`)·롤백(`rollback_live`)이 같은 엔진을 쓴다. 모의 실행용 `preview_apply`.
  - **`videos.update` 호출은 `_send_update` 단 한 곳**(소스 검사 TC-922·923). 쓰기 토큰은 `make_write_service`에서만 읽고(TC-924), 사람이 영상 ID를 입력한 **뒤** 11단계 맨 처음에만 호출된다(TC-571).
  - 요청 본문은 `build_write_body` 한 함수에서 정한다(`NOT_SENT_SNIPPET_FIELDS`, 지금은 비어 있어 snippet 전체 + 제목만 교체). 보내기 전 `check_body`가 제목 외 전부 일치하는지 검사한다.
  - 중단: 1~11단계 실패는 `aborted`(`GATE-nn`) 행 1개(감사). 11단계에서 `planned`가 생긴 뒤 쿼터 예약이 실패하면 그 행을 `aborted`로 끝낸다. 12단계에서 구글이 분명히 거절하면(400/401/403/429) `failed`, 반영 여부를 알 수 없으면(5xx·타임아웃·예상 못 한 예외·Ctrl+C) 재조회로 새 제목이 확인될 때만 성공으로 잇고 아니면 `planned`로 남긴다(자동 정리 없음). 재시도(최대 2회)마다 쿼터를 새로 선예약하고 실패해도 차감을 유지한다.
  - 사후 검증 실패: `success` + `verify_result_json.ok=false`, 큰 경보 + `rollback` 명령 안내, **자동 롤백 없음**.
- `commands/apply.py`: `apply --candidate N [--live]`. `--live` 없으면 plan과 같은 정보 + 14단계 조건 표(막는 단계와 해결 방법)만 출력(쓰기·구글 연결 없음, 막힌 단계가 있으면 종료 코드 3). 후보 1건씩만(일괄 옵션 없음).
- `commands/approve.py`: `approve --candidate N --approver 이름 [--ttl-hours H]`. 계획 요약 → 영상 ID 직접 입력 → 승인 파일 생성 + 후보 `filtered→approved`. 이미 유효한 승인이 있으면 `덮어쓰기` 입력을 추가로 요구.
- `commands/rollback.py`: `--live`(+`--approver` 필수)를 live_guard 롤백 엔진에 연결. 교체 제한·변경 전 지표 확인은 WU-4 결정대로 면제하고, 승인 파일 대신 확인자 이름 + 영상 ID 직접 입력이 사람의 승인이다. 롤백도 enable_live·허용 목록·쿼터·미확정 기록·재조회(제목·계획 해시)를 모두 거친다.

## 2. 설계서 대비 편차와 사유
| # | 편차 | 사유 |
|---|---|---|
| 1 | 승인 파일에 `v`, `used_at`, **`mac`(HMAC-SHA256)** 추가. 키는 `<토큰 폴더>/approval_hmac.key`(첫 `approve`가 생성, 검증 경로는 절대 생성하지 않음) | 위조·만료 연장·`used` 되돌리기를 파일만 고쳐서는 못 하게(T-03). 설계 EVT-202의 8개 항목에 추가이므로 **질문 1** |

| 3 | 11단계 순서: 쓰기 토큰 로드 → DB 사본 → 승인 소진 → planned 행 → 쿼터 예약. 토큰 실패·백업 실패는 승인을 소진하기 **전에** 막힌다 | 토큰/백업 문제로 승인이 낭비되지 않게. 토큰은 사람 확인(10단계) 이후에만 읽는다 |
| 4 | 5단계에 **결과 미확정 `planned` 행 점검** 추가(영상 단위, 적용·롤백 모두 거부) | 오케스트레이터 결정 3. 자동 삭제 없음(질문 2) |
| 5 | 승인 `approve`는 교체 제한/쿼터를 지금 통과하지 못하는 계획이면 승인하지 않음(종료 코드 3). `--ttl-hours`는 설정값 `approval.ttl_hours`를 넘길 수 없음 | 승인은 '지금 실행 가능한 계획'에 대한 서명이어야 하고 유효 시간은 설정이 상한이라서 |
| 6 | 12단계 호출 오류를 '분명한 거절(failed)'과 '반영 여부 불명(planned)'으로 나눔. 불명이면 읽기 1회로 확인 | 설계에 없는 상황(타임아웃)에서 이중 적용·유실 기록을 막기 위해. fail-closed |
| 7 | 사후 검증 비교 항목: description·tags·categoryId·defaultLanguage·defaultAudioLanguage가 같아야 성공. `localized`와 그 밖의 항목 변화는 이름만 알림(실패 아님) | 설계는 '설명·태그·카테고리'만 명시. 나머지의 실제 변화는 12단계 실측 후 조정([확인 필요]) |
| 8 | 8단계(변경 전 지표 없음)의 '사용자 확인'은 `지표없이진행`을 직접 입력 | y/n 습관적 Enter 방지(UX 3장) |
| 9 | 승인/중단 화면: 1~9단계 결과는 진행 중에 줄마다 찍지 않고 10단계 요약표(또는 중단 시 표)로 한 번에 보여 줌 | SCR-005 '조건 체크 표' |
| 10 | `rollback`에 `--approver` 옵션 추가(live에서 필수) | WU-4 `begin_rollback`이 확인자를 요구 |
| 11 | `updater.execute_update`(항상 거부하는 자리)와 `UpdateGateway`는 그대로 둠 | WU-4 테스트(TC-451~453)가 고정. 실제 쓰기는 live_guard가 하며 이 자리는 쓰이지 않음 |

## 4. 수동 확인이 필요한 부분 ([확인 필요])
- **읽기 전용 필드 포함 snippet 전체 전송**(thumbnails·publishedAt·channelId 등): API가 수락하는지·무시하는지 미확인. 12단계 비공개 테스트 영상에서 확인하고, 거부되면 `live_guard.NOT_SENT_SNIPPET_FIELDS`에 이름만 추가하면 본문 구성과 본문 검사가 함께 바뀐다(TC-930이 이 고리를 고정, TC-572는 지금의 '전체 전송'을 고정하므로 함께 고칠 것).
- 사후 검증 비교 항목(편차 7)과 `videos.list` 직후 재조회가 항상 최신 값을 주는지(최종 일관성).
- 쓰기 범위(scope) 최소화는 WU-1 노트의 미확인 사항과 동일.
- Windows: 승인 파일·키 파일 권한 제한(`icacls`)은 이 환경(Linux)에서 검증하지 못함. 콘솔 폭에서 14단계 줄 길이.
- 동시에 두 `apply --live`가 같은 후보를 처리하는 경합은 막지 않는다(1인 CLI 가정). 승인 소진과 planned 행 확인 사이의 틈은 마이크로초 단위.

**질문**(진행을 막지 않음)
1. 승인 파일에 HMAC 인증값을 추가하고 키를 토큰 폴더에 두는 편차(편차 1)를 승인하시나요? 반대하면 `mac` 검사만 빼면 되지만, 파일 수정으로 만료 연장·used 되돌리기가 가능해집니다.
2. **오래된 `planned` 행 정리 방법**(비정상 종료로 남은 것): 지금은 그 영상의 적용·롤백을 모두 거부하고 안내만 합니다. 사람이 Studio에서 제목을 확인한 뒤 `planned`를 `failed`/`success`로 확정하는 전용 명령(예: `history resolve`)을 만들지, 수동 SQL 안내로 둘지 결정 필요(WU-5 범위 밖이라 만들지 않음).
3. 불명 오류 뒤 재조회에서 '새 제목'이 아닌 다른 제목이 보이면 `planned`로 남깁니다. 이 보수적 처리(최종 일관성 때문에 '미반영'으로 단정하지 않음)가 맞는지 확인 부탁드립니다.
4. 롤백의 사람 승인을 승인 파일이 아니라 '확인자 이름 + 영상 ID 직접 입력'으로 정의했습니다(EVT-007 게이트 목록과 동일). 롤백에도 승인 파일을 요구할지 확인 부탁드립니다.
5. 12단계 전 읽기 전용 필드 전송 확인 방법(공식 문서 재확인 vs 비공개 영상 실측) 결정 필요(WU-4 질문 4와 동일, 후크는 준비됨).
