# unit-6 구현 노트 — WU-6 성과 리포트·CSV 가져오기 (5단계)

- 작업 단위: **WU-6** (feature F-D 성과 리포트) / **속도 트랙: L3** / Tier: Standard / 선행: WU-2, WU-4(스키마·`title_changes` 기록 형식만 참조, 코드 의존 없음)
- 실행: WU-4(updater/limits/history/plan/rollback)와 **병렬**로 서브에이전트가 수행. 파일 범위 겹침 없음(아래), 다른 에이전트 파일은 읽기만 했고 수정하지 않음.
- 파일 범위: `src/ytitle/{report,csv_import}.py`, `src/ytitle/commands/report.py`, `tests/test_{report,csv_import,report_cmd}.py`, 이 노트. 신규 의존성 없음(표준 `csv`·`sqlite3`·`zoneinfo`만). 네트워크·YouTube 호출 없음.

## 1. 구현 범위
- `csv_import.py`: Studio 내보내기 CSV를 **신뢰할 수 없는 외부 입력**으로 읽는다. 크기 5MB·데이터 행 10,000 상한, UTF-8(BOM 허용)·UTF-16(BOM)·CP949 해석, 바이너리(NUL) 거부, 구분자(쉼표·탭·세미콜론) 자동 판별, 한글/영문 머리글 별칭 인식(표기 차이 무시), 숫자·퍼센트 파싱(쉼표 천단위, `3.2%`), 수식 시작 문자(`= + - @`)·지수 표기·NaN·무한대 거부, 영상 ID 형식 검증, 불량 행 건너뛰기(줄 번호·이유 수집), 같은 영상 중복 줄 무시(첫 줄 사용), 합계 행 건너뜀, 머리글 오류는 한 번에 모아 보고. 저장은 `metrics_snapshots`(`source='csv'`)에 **한 번의 트랜잭션**(전부 또는 전무), 같은 내용 재가져오기는 중복 저장하지 않음.
- `report.py`: DB(`title_changes`·`metrics_snapshots`·`videos`)를 **읽기 전용 SELECT**로 조회(`load_video_data`, `list_changed_video_ids`)하고, 순수 함수 `build_report`로 전후 비교를 계산. 데이터가 부족하면 `status="insufficient"`로 수치 비교를 만들지 않으며, 판정(효과 있음 등) 필드 자체가 없다. 면책 상수(`LIMIT_NOTE`, `CAUSAL_NOTE`)는 명령이 항상 출력.
- `commands/report.py`: `report [--video ID] [--import-csv 파일 [--phase P] [--period-start D --period-end D]] [--plain]`. 출력은 SCR-008 형식(변경 이력 표, 전후 표 또는 '데이터 부족' 사유, 한계 문구, 면책 푸터). 외부 문자열은 `sanitize_for_display`(CSV 유래 문자열은 추가로 수식 문자 무력화).

## 2. 설계서 대비 편차와 사유
| # | 편차 | 사유 |
|---|---|---|
| 1 | 머리글 별칭을 `config/csv_mapping.yaml`(EVT-203)이 아니라 **`csv_import.py` 안의 표**로 둠 | `config/`는 이 단위의 파일 범위 밖이고 실제 Studio 머리글을 확인하지 못했다. 다르면 표(`_ALIASES_READABLE`)만 고치면 된다 → 질문 1·5 |
| 2 | 옵션 `--phase`(before/after/periodic, 기본 periodic), `--period-start`, `--period-end` 추가(`--import-csv`와 함께만 허용) | 전후 비교는 단계·집계 기간을 알아야 한다. EVT-008에는 없던 옵션이라 추가 |
| 3 | `--video`는 가져오기와 함께 쓰면 **영상 ID 열이 없는 CSV의 대상 영상**(한 줄만 허용)이 되고, 가져온 뒤 그 영상 리포트를 보여 준다. ID 열이 있으면 필터가 아니라 리포트 대상 지정으로만 쓰임 | 한 영상짜리 내보내기 파일 대응. 필터 의미까지 넣으면 혼란스러워 단순화 |
| 4 | 옵션 없이 `report`는 **성공한 적용 기록이 있는 모든 영상**(최근 변경 순, 최대 20개) | EVT-008에 무옵션 동작이 없어 가장 자연스러운 동작 선택 |
| 5 | 파일 인코딩에 **CP949·UTF-16(BOM)** 도 지원 | DESIGN 9장 WU-6 검증 방법이 "UTF-8·CP949 테스트"를 요구, 엑셀 저장 대응 |
| 6 | 파일 위치 제한 없음(`.csv` 확장자·일반 파일·5MB만 검사). 상대 경로는 `settings.base_dir` 기준 | DESIGN에 CSV 위치 정책이 없고 Studio 내보내기는 보통 다운로드 폴더에 있어 제한이 오히려 방해. 읽기 전용이며 사용자가 직접 지정 → 질문 3 |
| 7 | `시청 시간(단위: 시간)` 열은 ×60해 `watch_minutes`에 저장. 단위를 알 수 없는 `시청 시간` 단독 열은 **무시**(추측 금지) | DB 열이 `watch_minutes`. 실제 Studio 단위 미확인 |
| 8 | **CTR은 퍼센트 단위(3.2 = 3.2%)로 저장**, `%` 유무와 관계없이 0~100으로 해석 | Studio 표기 기준. API가 저장하는 `ctr`의 단위는 미확인이라 단위가 다르면 전후 혼합 비교가 틀어질 수 있음 → 질문 2 |
| 9 | 비교 기준값: 노출수 최소 = 설정 `cadence.min_impressions_before_rechange`(기본 1,000)를 변경 전·후 **각각**의 기간 합계에 적용, 집계 기간 최소 7일(코드 상수, 임의 기본값), 변경 후 지표 수집 예정일 = 적용일 + `sequential_mode.evaluation_window_days` | 설계에 '데이터 부족' 수치 기준이 없음(규칙 A: 임의 기본값이므로 질문 4에 올림) |
| 10 | 기준선 인정 조건: 집계 **종료일 < 변경일(UTC 날짜)**, 변경 후 인정 조건: 집계 **시작일 > 변경일**. 기간이 없으면 수집 시각(`taken_at`)으로 가르되 기간 정보 없음으로 '데이터 부족' | 변경 당일분 혼입 방지(엄격). 쿼터와 달리 Analytics 날짜는 태평양 기준일 수 있어 ±1일 오차 가능 → 보수적 쪽 |
| 11 | 개수 지표(노출·조회·시청 시간)는 **하루 평균**으로 비교, 클릭률은 그대로 | 전·후 기간 길이가 달라도 비교 가능하게 |
| 12 | 변경 이후 **롤백이 있으면 '데이터 부족'**, 변경이 여러 번이면 가장 최근 적용 기준 + 안내 | 롤백 이후 자료는 두 제목이 섞임 |
| 13 | 제목 줄은 `모의 실행(dry-run)` 표기(DB에 지표를 쓰는 `--import-csv` 포함) | YouTube 쓰기가 없고 `ui.title_line`에 'LIVE가 아닌' 모드는 이것뿐 |
| 14 | 변경 시각은 한국 시간(`YYYY-MM-DD HH:MM`)으로 표시 | 04 UX 날짜 규칙 |

## 4. 수동 확인이 필요한 부분
- **실제 YouTube Studio 내보내기 CSV**의 머리글·시청 시간 단위·합계 행 형식은 확인하지 못했다(합성 샘플만 사용). 실제 파일로 한 번 `report --import-csv`를 돌려 `인식한 열`/`무시한 열`/`건너뛴 행` 출력을 확인해야 한다.
- API 경로(`fetch --metrics`)가 저장하는 `ctr`의 단위(비율 vs 퍼센트)와 CSV(퍼센트) 단위가 같은지는 실제 응답으로 확인해야 한다(편차 8).
- '데이터 부족' 기준(노출 1,000회·기간 7일)이 이 채널 규모에 적절한지는 사용자가 정해야 한다. 통계적 유의성 검정은 하지 않는다(수치를 나란히 보여 줄 뿐이며 원인을 단정하지 않는다).
- Windows 콘솔에서의 한글 폭 정렬·CP949 파일 실측은 이 Linux 환경에서 못 했다(미수행: Windows 필요).

## 7. 오케스트레이터에게 (요청·질문 — 진행을 막지 않음)
